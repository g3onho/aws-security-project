## 1. 먼저 — `app.js` 가 파싱되지 않고 있었다

`drawDetail()` 의 `APPROVED` 분기가 이렇게 커밋돼 있었다.

```javascript
buttons+='<button ... data-action="execute">${config.mode==='live'?(...):'데모 조치 실행'}</button>';
```

**작은따옴표 문자열 안에 `${...}` 를 썼다.** 안쪽의 `'live'` 가 문자열을 끊어 `live` 가
식별자로 읽히고, 파일 전체가 `SyntaxError: Unexpected identifier 'live'` 로 죽는다.
`app.js` 는 `<script type="module">` 이라 **모듈 하나가 통째로 로드되지 않는다** — 필터도
표도 지도도 동작하지 않는 상태였다.

이게 오래 남아 있던 이유는 테스트가 API 만 봤기 때문이다. 이 커밋 시점에도 백엔드
pytest 114개는 전부 초록이었다. 그래서 같이 넣은 것:

| 검사 | 위치 | 잡는 것 |
|---|---|---|
| `node --check` | `backend/tests/test_frontend_syntax.py` | JS 파싱 오류 전부 (Node 없으면 skip) |
| id 대조 | 같은 파일 | `app.js` 가 찾는 `#id` 가 템플릿에 없는 경우 |
| jsdom 렌더 | `frontend/tests/dom-check.mjs` | 5개 화면 렌더 중 런타임 오류, 데이터 미연결 회귀 |

`dom-check.mjs` 는 실제 Flask 응답을 픽스처로 쓴다(`backend/tools/dump_fixtures.py`).
계약이 바뀌면 화면 테스트도 같이 따라온다.

## 2. 인프라 모니터링 — 시간축

### 2.1 원인

`data.js` / `demo.py` 의 지표 생성기가 곡선 인덱스를 이렇게 잡았다.

```javascript
const atOffset = offset => { const k = Math.floor(offset) % 12; ... }
```

`offset` 은 "몇 시간 전"이다. 표본은 항상 12개이고 `offset = endOffset + (11-i)*hours/11` 이다.

- **1시간 구간**: offset 이 0.0 … 1.0 → `floor` 가 전부 0 (마지막만 1) → **값이 한두 종류뿐인 직선**
- **6시간**: 0.55시간 간격 → 12구간에 계단 6개
- **24시간**: offset 0~24 → `%12` 로 감싸 **같은 곡선을 두 바퀴**
- **7일**: 15.3시간씩 점프 → 시각과 아무 관계 없는 톱니

즉 x축은 시간처럼 생겼지만 y값은 시간의 함수가 아니었다. 실제 측정값:

```
1h  cpu: [61, 58, 58, 58, 58, 58, 58, 58, 58, 58, 58, 58]   ← 직선
24h cpu: [58, 44, 65, 81, 68, 61, 47, 57, 86, 73, 64, 58]   ← 시각 무관
```

### 2.2 To-Be

곡선을 **표본의 절대 시각(KST)** 으로 잡고 선형 보간한다.

```
x = ((at + 9h) mod 24h) / 2h        # 하루를 12구간
value = lerp(curve[i], curve[i+1]) + 호스트 시드 + 환경 보정 + 시각 결정 지터
```

지터는 `((floor(at/1000)+salt) % 100003 * 48271) % 2^31-1` 로 만든다. 정수 연산만 써서
JS 와 Python 이 같은 값을 낸다(난수 아님 — 같은 시각이면 항상 같은 값).

표본 주기는 CloudWatch 처럼 적응형이다.

| 기간 | period | 표본 수 | 이전 |
|---|---|---|---|
| 1시간 | 5분 | 13 | 12 (직선) |
| 6시간 | 5분 | 73 | 12 |
| 24시간 | 15분 | 97 | 12 |
| 7일 | 3시간 | 57 | 12 |
| 31일 | 6시간 | 125→121 | 12 |

후보는 `300 / 900 / 1800 / 3600 / 10800 / 21600`초, 표본 상한 121개.

**성질 하나가 생긴다 — 기간을 바꿔도 같은 시각의 값은 같다.** 24시간 구간과 6시간 구간이
겹치는 표본은 값이 동일하다. 테스트로 고정했다(`test_same_instant_has_same_value_in_every_window`).

### 2.3 `/api/metrics` 응답 확장

```jsonc
{
  "resource": "i-seoul-app-01",
  "host":   {"id":"...","name":"docker-host","role":"3-Tier 컨테이너 호스트","type":"t3.small","tier":"app"},
  "hosts":  [ … 리전의 EC2 목록 … ],          // 화면 호스트 선택기
  "period": 900,                               // 표본 주기(초)
  "window": {"from":…, "to":…},
  "points": [{"at":…, "cpu":…, "memory":…}],
  "threshold": {"cpu":80, "memory":80},
  "breaches": [{"metric":"cpu","from":…,"to":…,"peak":86.6,"samples":4}],
  "summary": {"cpu":{"max":…,"avg":…,"last":…}, "memory":{…}, "samples":97}
}
```

`breaches` 는 임계치를 **연속으로** 넘은 구간을 하나로 묶은 것이다. 화면은 이걸로
"몇 시부터 몇 시까지, 최고 몇 %, 표본 몇 개"를 보여준다.

> 주의: `breaches` 는 화면 표본 기준이라 CloudWatch 알람(5분 평균 2회 연속)과 1:1이 아니다.
> 화면에도 그렇게 적었다.

## 3. 3계층 서비스 연동

### 3.1 원인

`index.html` 이 아니라 `app.js` 의 `infrastructure()` 안에 이렇게 박혀 있었다.

```javascript
<div class="service-node">Nginx<span>○ 미연동</span></div>
… <div class="context-note">각 서비스의 실제 상태 점검: 미연동<br>실제 AWS 조회 및 조치: 미연동</div>
```

상태를 넣을 자리는 있는데 **그 자리를 채우는 데이터 경로가 아예 없었다.**
백엔드에도 3계층을 다루는 코드가 없었다. 그래서 API 부터 만들었다.

### 3.2 `GET /api/services`

```jsonc
{
  "region":"ap-northeast-2","checkedAt":…,"mode":"demo","overall":"DEGRADED",
  "target":"i-seoul-app-01","intervalSec":30,
  "items":[
    {"id":"nginx","name":"Nginx","tier":"web","port":80,
     "status":"UP",             // UP | DEGRADED | DOWN | UNKNOWN
     "detail":"정상 응답",
     "latencyMs":10.5,"errorRate":0.0,

     "target":"i-seoul-app-01","probe":"GET http://i-seoul-app-01/ (ALB 대상 그룹)",
     "dependsOn":null,"source":"데모 시계열 + 미해결 이벤트",
     "blockers":[{"id":"EVT-0003","scenario":"SEC-02","title":"…","severity":"MEDIUM"}]}
  ], "note": null

```

### 3.3 판정 규칙 — 데모/로컬 (`app/services/tiers.py`)

화면의 다른 숫자와 **맞물리게** 만든 것이 핵심이다. 난수였으면 "왜 지금 저하냐"에 답할 수 없다.

| 입력 | 규칙 |
|---|---|
| 부하 계수 `max(CPU, 메모리) / 80` | `> 1.0` → Flask·MySQL **DEGRADED**, `> 1.15` → **DOWN** |
| 미해결 이벤트 | 계층 매핑 시나리오가 미해결이면 **DEGRADED** + 근거 이벤트 표시 |
| 의존성 | 상류가 DOWN 이면 하류는 정상이어도 DEGRADED (요청이 도달하지 않음) |
| 응답시간 | `기준값 × (1 + max(0, 부하-1)×2.6) × (저하면 1.8)` |

계층 ↔ 시나리오 매핑:

| 계층 | 시나리오 | 이유 |
|---|---|---|
| Nginx | SEC-02, SEC-08 | 보안 헤더 누락 / 웹 애플리케이션 공격 |
| Flask | SEC-07 | 자격증명 하드코딩·.env 노출 |
| MySQL | SEC-03, SEC-06 | 3306 과다 공개 / 무차별 대입 |

### 3.4 판정 규칙 — 실모드 (`app/adapters/live.py`)

신호가 두 갈래다. **`enable_alb` 가 기본 false 라, ALB 가 없는 배포가 정상 경로다.**
ALB 만 보면 실제 배포에서 Nginx·Flask 가 영원히 UNKNOWN 으로 남는다.

**① ALB 가 있을 때**

| 계층 | 조회 | 판정 |
|---|---|---|
| Nginx | `elbv2:DescribeTargetGroups` + `DescribeTargetHealth` | 정상 대상 0 → DOWN, 일부 → DEGRADED |
| Flask | CloudWatch `AWS/ApplicationELB` `TargetResponseTime`(p95) · `HTTPCode_Target_5XX_Count` · `RequestCount` | 5XX ≥ 5% → DOWN, 5XX > 0 또는 p95 > 1s → DEGRADED |

**② ALB 가 없을 때 — CloudWatch Logs 폴백**

CloudWatch Agent 가 이미 보내고 있는 로그를 읽는다
(`compute/templates/docker-host.sh.tftpl:44-46`, `mysql-db.sh.tftpl:57-59`).
대시보드 역할에 `logs:FilterLogEvents` 가 이미 있어 권한 추가가 필요 없다.

| 계층 | 조회 | 판정 |
|---|---|---|
| Nginx | `/<project>/<env>/web/nginx` 요청 로그 + `?"[error]" ?"[crit]" ?"[emerg]"` | error 있음 → DEGRADED · 요청 로그 0 → UNKNOWN · 그 외 UP |
| Flask | 같은 그룹의 error 중 `upstream` 포함 건 | ≥5건 → DOWN · 1건 이상 → DEGRADED · 0건이고 요청 있음 → UP |
| MySQL | `/<project>/<env>/db/mysql` 의 `?"[ERROR]" ?"Access denied"` + CloudWatch 알람 | 알람 ALARM → DEGRADED · 오류 로그 있음 → DEGRADED · 그 외 UP |

Flask 를 `upstream` 오류로 보는 이유: Nginx 가 Flask 로 프록시하지 못하면
`connect() failed ... upstream` 이 error.log 에 남는다. ALB 도 `ssm:SendCommand` 도
없이 얻을 수 있는 유일한 앱 계층 실측 신호다.

로그 그룹 이름은 `LOG_GROUP_NGINX`·`LOG_GROUP_MYSQL` 환경변수를 먼저 보고,
없으면 `NAME_PREFIX`(`<project>-<env>`)에서 유도한다. 유도에 실패하면 빈 문자열이고
해당 계층은 UNKNOWN 이다 — **추측해서 틀린 그룹을 읽지 않는다.**

**조회 실패는 502 로 올리지 않는다.** 해당 계층만 `UNKNOWN` + 이유 문구로 떨어뜨리고,
전부 UNKNOWN 이면 `note` 에 무엇을 켜야 하는지 적는다.

> **운영 주의(README 2-2와 연결)**: NAT 를 끄면 CloudWatch Agent 전송이 끊겨 로그 폴백도
> 같이 죽는다. 화면의 "요청 로그가 없습니다 / Agent 전송이 끊겼습니다" 가 그 신호다.

### 3.5 화면

계층 노드 3개(상태 색·응답시간·오류율) + 계층별 표(상태·응답·판정 근거·점검 대상·점검 주기).
근거가 된 이벤트는 눌러서 상세로 이동한다. 점검 주기와 마지막 점검 시각을 함께 적어
"언제 기준 상태인지"를 화면에서 알 수 있게 했다.

## 4. 조치 동선과 그 밖의 보완

### 4.1 취약점 점검 표의 조치 버튼

As-Is: 표는 읽기 전용. 조치하려면 이벤트를 눌러 상세 창을 열고, 거기서 승인 → 다시 열어 실행 →
다시 열어 재검증. 취약점을 눈으로 확인하고도 표에서 할 수 있는 게 없었다.

To-Be: 표에 **조치 열**을 넣고 현재 상태에 맞는 버튼 하나를 띄운다.

| 상태 | 버튼 |
|---|---|
| 신규 / 승인 대기 / 실행 실패 | **승인** |
| 승인됨 | **조치 실행** |
| 재검증 대기 / 재검증 실패 | **재검증** |
| 조치 실행 중 / 재검증 중 | 진행 중 (비활성) |
| 해결 | 완료 (비활성) |
| 자동 대응 경로 · 등록된 수동 조치 없음 | "자동 대응" 표기 (버튼 없음) |
| `WRITE_ENABLED=false` 또는 viewer | "조회 전용" 표기 |

버튼은 상세 창과 **같은 API·같은 가드**를 탄다 — `expected_status` + `plan_hash` + `Idempotency-Key`.
승인 이후 대상이나 변경 내용이 달라지면 409 로 막히는 것도 그대로다. 표에서 누른다고
검증이 느슨해지지 않는다.

**일괄 승인**: 선택 열 체크박스 + "선택 일괄 승인". 항목마다 순차로 승인하고 성공/실패 건수를
한 줄로 보고한다. 실행·재검증은 일괄로 두지 않았다 — 되돌릴 수 있는 조치만 자동화한다는
원칙(README 2-3)에 맞춰 실제 변경은 건별 확인을 남긴다.

### 4.4 침해사례 탭 (v2.4.0)

설계안 12장의 대시보드 파트 책임은 "Flask 대시보드, **실제 API 연동**, **침해사례 탭**,
**승인 워크플로우**" 넷이다. 나머지 셋은 있었는데 **침해사례 탭은 화면 자체가 없었다.**

시나리오(SEC-01~10)마다 **공격 → 탐지 → 승인 → 조치 → 재검증** 을 한 줄로 세운다.

| 단계 | 완료 근거 | 시각 |
|---|---|---|
| 공격 재현 | **없음 — 절대 자동 완료되지 않는다** | — |
| 탐지 | 해당 시나리오 이벤트 존재 | 가장 이른 `at` |
| 승인 | `approvedAt` 이 있는 이벤트 | 가장 이른 `approvedAt` |
| 조치 실행 | `execution == "SUCCEEDED"` | 이력의 `auto-executed`/`execute`/`completed` |
| 재검증 | `verification in (PASSED, FAILED)` | 가장 늦은 `afterAt` |

**카탈로그에 적혀 있다고 단계가 켜지지 않는다.** 발표 화면에서 "문서에 있는 것"과
"실제로 일어난 것"이 구분돼야 하기 때문이다. 특히 '공격 재현'은 절차가 카탈로그에 있어도
완료로 표시하지 않는다 — 실행 여부를 시스템이 알 수 없다.

카드에는 탐지·미해결·재검증 실패 건수, 자동/수동 분류, 플레이북 배선 여부, 가역성이 붙고,
접었다 펴는 상세에 공격 재현 절차·흔적이 남는 위치·영향·대응·판정 기준·근거 문서가 들어간다.
**기획서 분류(`planned_mode`)와 코드 기준(`mode`)이 다르면 카드에 그대로 노출한다** —
SEC-02(`ASR-HardenNginx` 미배선)가 여기 해당하고, 발표에서 "자동 3개"라고 말하지 않게 된다.

서술 카탈로그는 `scenarios.yaml` 과 **분리했다**(`app/catalog/incidents.yaml`).
`scenarios.yaml` 은 실 AWS finding 을 SEC-xx 로 분류하는 **동작** 카탈로그라, 발표 문구를
고치다 분류 규칙을 건드리면 탐지가 조용히 틀어진다. 테스트로 두 파일의 역할 분리를 고정했다.

### 4.5 취약점 점검 실데이터화 (v2.5.0)

- As-Is: `/api/vulnerabilities` 구현돼 있었으나 **프론트가 한 번도 호출하지 않음.** 데모 응답의
  `cveId`·`cvss`·`package`·`installedVersion`·`fixedVersion`·`reportKey` 전부 `null`.
- To-Be: `app/catalog/vulnerabilities.yaml` 신설 — 대상 8개(ECR 이미지 4 + EC2 4), **CVE 299건 / 고유 55건**.
  생성기 `backend/tools/gen_vulnerabilities.py`.
- 화면: 대상 카드(심각도 분포 · 수정 가능 건수 · 스캔 시각 · **조치 버튼**) + CVE 표(심각도·CVSS·CVE·패키지·설치→수정·대상).
- 조치 단위는 CVE 가 아니라 **대상**이다 — 이미지 교체 / 패키지 업데이트. 버튼은 상세 창과 같은 가드를 탄다
  (`expected_status` + `plan_hash` + `Idempotency-Key`).
- 기간 필터를 적용하지 않는다. 스캔 결과는 이벤트가 아니라 **최신 상태**다. 15분 구간을 골랐을 때
  목록이 비면 "취약점이 없다"로 읽힌다. 대신 대상별 스캔 시각을 같이 내보낸다.
- **카탈로그는 데모 전용.** CVE ID·패키지명은 공개 정보를 참고했으나 CVSS·버전은 화면 검증용 표기값이며
  NVD 원본과 다를 수 있다. 실모드 정본은 Inspector2 `ListFindings` + S3 의 Trivy 리포트다.

### 4.7 인프라 모니터링 재설계 (v2.5.0)

- **운영 중인 서버 전부 표시** — `GET /api/metrics?scope=all` 이 리전의 EC2 전량 시계열을 한 번에 준다.
  화면은 호스트 카드(CPU·메모리 게이지, 임계선, 초과 구간 수)로 깔고, 카드를 누르면 상세 차트가 바뀐다.
  이전에는 리전당 자원 1개 고정이었다.
- **기간 프리셋 재설계** — `1시간/6시간/24시간/7일` → **`15분/1시간/1일/1주일`**.
  표본 주기 후보에 **60초**를 추가했다. 15분을 5분 주기로 그리면 표본이 3개뿐이다.

| 기간 | 표본 주기 | 표본 수 |
|---|---|---|
| 15분 | 1분 | 16 |
| 1시간 | 1분 | 61 |
| 1일 | 15분 | 97 |
| 1주일 | 3시간 | 57 |

### 4.8 CVE 재검증 (v2.6.0)

- `_verify_cve_count()` 가 `_call(maxResults=100)` 1회라 **100건 초과분을 못 셌다.** 재검증 수치가
  실제보다 작게 나와 "개선됐다"로 잘못 읽히는 경로였다. `_pages()` 로 교체.
- 심각도 기준을 카탈로그 `verify.min_severity` 로 분리. SEC-04 는 `null`(전체 심각도).
- **SEC-04 재검증: `trivy_report_diff` → `inspector_cve_count`**, Trivy 는 `alternates` 병행.
  Inspector2 가 ECR 이미지도 스캔하므로 `ssm:SendCommand`(T6) 없이 자동 재검증이 된다.
- 재검증 불가 시나리오가 SEC-02·04·07 3개 → **SEC-02·07 2개**로 줄었다.

### 4.9 SEC-06 NACL 차단 폼 (v2.6.0)

- `GET /api/nacls` 신설 — NACL 목록 + 사용 중인 Deny 규칙 번호(1~99) + 빈 번호 자동 제안.
  `ec2:DescribeNetworkAcls` 권한은 기존 `dashboard_read` 에 이미 있다.
- 상세 창 폼 → `POST /api/events/:id/plan` → `PENDING_APPROVAL` → 기존 승인·실행 흐름.
- 출발지 IP 는 탐지값 읽기전용. 다른 값을 보내면 서버가 409(`STATE_CONFLICT`).
- 데모 모드는 폼만 표시하고 제출 없음 — 계획 설정은 실 AWS 검증이 전제다.

### 4.10 알림 발송 (v2.6.0) — 기능을 만들지 않고 **제거**했다

- 설계안 5-2·5-3 기준 SNS 발행 주체는 CloudWatch 알람(`alarm_actions`)과 `asr_trigger`(`sns.publish`)다.
  대시보드가 보내는 흐름은 설계안에 없다. `POST /api/events/:id/notify` 는 근거 없는 surface 였다.
- 제거 범위: notify/notifications 라우트 2개, `live_service.notify()`, `ALLOWED['notify']`,
  `_change` 의 notify 분기, `flush_notifications()`, `notification_status()`, `notifications` 테이블 DDL, 테스트.
- 대체: 이벤트에 `notification` 필드(`at`·`channel`·`source`·`reason`·`count`)를 실어
  **"알림이 갔는지"** 만 표시한다. 상세 창 메타 + 전용 섹션.
- 라우트가 **없는지**를 검사하는 테스트를 넣어 재발을 막았다.

### 4.11 주소창 상태 동기화 (v2.6.0)

- 담는 것: `view`·`region`·`resource`·`hours`·`back`·`severity`·`status`·`source`·`q`·`page` + `event`.
  기본값은 넣지 않아 주소가 짧게 유지된다.
- 히스토리는 **화면 전환·상세 열기만** push. 검색어 입력마다 쌓이면 뒤로가기를 못 쓴다.
- `popstate` 에서 상태 복원 + 상세 창 열고 닫기. 최초 로드도 같은 경로를 탄다.

| T4 | `dashboard.env` 에 `LOG_GROUP_NGINX` / `LOG_GROUP_MYSQL` 추가 | 동일 | **불필요.** `NAME_PREFIX`(`<project>-<env>`)에서 `/soar-sec/dev/web/nginx` 형태로 유도한다(`config.log_groups()`). 이름 규칙이 바뀌면 그때 필요 |
| T5 | user_data 에 대시보드 앱 코드 배포 단계 추가 | 동일 | 런타임(venv·환경파일)만 준비되고 앱이 뜨지 않는다. 그 전까지는 본인 PC 에서 `python awsrun.py` 로 실모드 접속 |
| T6 | `ssm:SendCommand` 권한 (SEC-02·04·07 재검증) | `modules/compute/iam.tf` (`dashboard_execute`) | 카탈로그 `needs_send_command: true` 로 막혀 담당자 증적 입력 경로로 간다 |

> T2·T3·T5 는 `dashboard.sh.tftpl` 변경이라 `user_data_replace_on_change = true` 때문에
> **dashboard EC2 가 교체된다.** 상태를 들고 있지 않은 인스턴스라 영향은 없지만, plan 에서
> `-/+ replace` 가 `aws_instance.dashboard` 에만 뜨는지 확인하고 apply 할 것.

## 6. (해소됨) 백엔드 취약점 100건 확대 → §4.5·§4.6 참고

> v2.5.0 에서 처리했다. 아래는 당시 설계 메모로 남긴다.

사용자 지시로 이번 회차에서는 넣지 않았다. 다음 회차용 설계만 남긴다.

현재 `GET /api/vulnerabilities` 는 이벤트에서 Trivy·Inspector 건만 골라 껍데기를 만들고
`cveId`·`cvss`·`package`·`installedVersion`·`fixedVersion`·`reportKey` 를 **전부 null** 로 돌려준다.
화면도 이 엔드포인트를 쓰지 않는다. 건수만 늘리면 null 컬럼만 100줄 늘어난다.

권장 순서:

1. **CVE 카탈로그 신설** — `app/catalog/vulnerabilities.yaml` 에 CVE ID·CVSS·패키지·설치/수정
   버전·영향 이미지/인스턴스를 가진 100건. 데모 전용임을 파일 헤더에 명시.
2. **어댑터 연결** — `DemoAdapter.vulnerabilities()` 가 카탈로그를 반환하고, 대표 건만 이벤트로
   승격해 지도·목록 건수가 폭주하지 않게 한다.
3. **화면** — 취약점 점검 표에 CVE·패키지·CVSS·수정 버전 열을 붙이고, 이미지 단위로 접는다.
   조치 버튼은 이미 §4.1 로 준비돼 있다.
4. **페이지네이션** — 100건이면 커서 페이지네이션(`filters.paginate`)을 그대로 쓸 수 있다.
   `MAX_LIMIT=200` 이므로 상한 조정은 필요 없다.
5. **실모드 정합** — `live.vulnerabilities()` 는 Inspector2 `ListFindings` + Trivy 리포트 S3 키를
   쓰므로, 카탈로그 스키마를 그 응답 모양에 맞춰 두면 교체 지점이 한 곳으로 모인다.
