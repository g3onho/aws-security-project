## 1. 상태와 기록 방식

- **확정**: 사용자 또는 지정된 책임자가 선택을 명확히 승인했다. 영향받는 문서와 계약을 갱신한다.
- **미결정**: 근거와 가능한 선택지는 정리했지만, 승인된 방향이 없다. 기능 목표나 기존 코드만으로 추정하여 확정하지 않는다.
- **대체됨**: 이후 결정이 과거 선택 또는 지시를 명시적으로 대체했다. 역사 기록은 남기되 현재 기준으로 사용하지 않는다.
- **검증된 현행 사실**: 코드나 자료에서 읽기 전용으로 관찰한 사실이다. 그 자체는 설계 승인이나 실환경 검증을 뜻하지 않는다.

각 항목은 결정 ID, 상태, 결정 내용 또는 질문, 근거, 영향 문서·기능, 재검토를 유발하는 조건을 가진다. 사용자 확인 날짜가 별도로 기록되지 않은 결정에는 임의 날짜를 넣지 않는다. 설계 선택을 바꾸면 기존 항목을 덮어쓰지 말고 새 결정과 대체 관계를 기록한다.

구현이 설계와 다르면 아래 중 하나로 분류하고 추적표에 근거를 연결한다.

- **구현 수정 대상**: 확정 설계가 유효하고 코드가 이를 충족하지 않는다.
- **설계 갱신 대상**: 요구사항·제약 변경이 확정되어 기존 설계를 바꿔야 한다.
- **임시 예외**: 승인된 이유·범위·종료 조건을 기록하고 제한된 기간 동안만 벗어난다.

미결정 상태는 임시 예외가 아니다. 미결정 설계에 맞추기 위해 기존 구현을 고치거나 운영 환경에 적용하지 않는다.

## 5. 미결정 질문 처리 절차

미결정 질문을 개발에 영향 주는 변경으로 처리하기 전에 다음을 따른다.

1. 질문 ID, 확인된 사실, 상충 근거, 결정이 필요한 역할과 선택지를 기록한다.
2. 선택마다 보안 영향, 구현·운영 영향, 복구 및 검증 영향을 설명한다.
3. 답변이 설계에 영향을 주면 해당 사용자의 명확한 선택을 결정 상태로 남긴다. 기술적 표현만의 수정은 새 정책 승인으로 해석하지 않는다.
4. 선택 후 README.md, 관련 기능 설계, 시나리오, glossary와 추적표를 갱신한다. 실제 코드 편차는 구현 수정 대상·설계 갱신 대상·승인된 임시 예외 중 하나로 분류한다.
5. 선택 전 수행한 독립 작업은 계속할 수 있지만 미결정 동작을 구현하거나 운영에 적용하지 않는다.

## 6. 구현·검증 기록과 변경 추적

이 문서는 “무엇을 선택했는가”를 기록한다. 코드가 실제로 무엇을 하는지, 어떤 경로가 선언·호출·연결되었는지, 테스트가 수행되었는지는 tracking.md에서 근거와 함께 기록한다. 문서에 적힌 결정이 실환경에 배포되었다고 추정하지 않는다.

다음 변경은 결정 기록을 검토한다.

| 변경 | 갱신할 기록 |
|---|---|
| 새 사용자 선택 또는 이전 선택 변경 | 새 DEC 항목, 이전 항목의 대체 상태, 영향 문서 |
| 확정 기준과 코드가 다름 | DEC의 분류·이유, tracking의 코드 경로·구현 상태·검증 상태 |
| 정책 수치 또는 재시도·보존·신선도 값 승인 | 근거, 소유자, 적용 범위, 검증 기준, 변경된 기능 문서 |
| 임시 예외 승인 | 예외 범위, 이유, 만료/종료 조건, 위험 소유자, 원복 검증 |
| 구현 상태나 검증 결과만 변경 | tracking만 갱신. 설계 결정 상태를 구현 완료로 바꾸지 않음 |

커밋 제목은 DEC-009 규칙만 사용한다. 해당 결정·구현·검증 상세는 변경 기록과 tracking에서 실제 커밋 SHA에 연결한다. 존재하지 않는 버전, 검증, 사용자 승인을 소급해서 작성하지 않는다.
