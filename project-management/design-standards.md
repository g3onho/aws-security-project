## 1. 기본 원칙

발표용 이미지는 승인된 설계를 읽기 쉽게 설명하는 보조 표현물이다. 이미지는 요구사항, 기술 계약, 운영 절차, 검증 증거의 정본이 아니다. 이미지와 Markdown 설계가 다르면 설계 문서가 우선하며, 그림은 바로잡는다.

생성형 AI는 배치와 시각 스타일을 제안할 수 있지만 구성요소, 데이터 흐름, 권한, 승인 조건, 자동화 여부를 추측하거나 새로 결정하지 않는다. 근거가 없는 요소는 생략하거나 “미결정”으로 표시한다. 코드 선언 또는 기존 그림에 있다는 이유만으로 기능이 구현·검증되었다고 나타내지 않는다.

전체 시스템 그림에는 프로젝트 설계의 네 계층을 사용한다. 세부 흐름 그림은 해당 기능 설계와 시나리오 범위에 맞춘다. 모든 이미지가 네 계층을 억지로 재현하거나 대시보드 기술을 다른 기능에 적용할 필요는 없다.

발표 자료가 여러 페이지일 때 **1번 페이지는 전체 아키텍처 완전판**이다. 프로젝트에서 사용한 기술(README의 “구현한 기술” 표의 모든 행)을 하나도 빼지 않고 담으며, 제작과 검수의 노력을 이 페이지에 집중한다. 2번 이후 페이지는 기능별 상세이며 해당 기능의 범위만 그린다. 완전판이 복잡해지는 문제는 요소를 덜어 내어 푸는 것이 아니라 배치 규칙(아이콘 하나에서 선 여러 개, 테두리 중첩, 그룹 박스, 3행 배치)으로 푼다. 리소스 식별자, 이벤트 계약, 긴 조건 주석은 그림에 넣지 않고 README와 기능 설계 문서에 둔다.

위 색상은 표현 토큰이다. 전체 그림은 **AWS 공식 테마**를 따른다. 서비스 아이콘과 VPC·서브넷·EC2 그룹 프레임의 색은 AWS 공식 아키텍처 아이콘 패키지 가이드를 그대로 쓰고 임의로 지정하지 않는다. 계층 헤더와 제목은 위 AWS 다크 네이비를 쓴다. 현대오토에버 색은 원본 로고 안에서만 사용한다. 제3자 제품의 공식 로고 색상도 해당 로고 안에서 유지할 수 있다. 이 예외를 계층 밴드의 색상이나 흐름 색상 의미를 바꾸는 데 사용하지 않는다. 공격 강조색(#C8102E)과 혼동될 수 있는 빨간 프레임은 그룹 프레임에 쓰지 않는다.

공격 경로는 빨간 점선, 정상 요청은 파란 실선, 로그 수집은 회색 실선, 데이터 조회는 보라 점선, 실제 자동 조치는 하늘색 실선으로 구분한다. 각 선에는 가능한 한 “요청”, “로그”, “조회”, “실행” 같은 짧은 한국어 설명을 붙인다. 선 색만으로 의미를 전달하지 않는다. 화살표 방향, 선 종류, 범례, 라벨을 함께 사용한다.

무지개색 팔레트, 네온 효과, 의미 없는 그라데이션, 과도한 3D, 장식용 그림자와 경고색의 남용은 사용하지 않는다. 성공·실패·미확인 상태가 필요한 그림은 색상과 텍스트·기호를 함께 써서 구분하고, 상태색이 위 흐름 범례와 충돌하지 않도록 한다.

### 2.2 캔버스와 배치

전체 아키텍처와 기업 발표용 기본 캔버스는 16:9 가로형, 4K UHD(3840×2160 픽셀), 흰색 바탕으로 한다. 최종 PNG의 실제 픽셀 크기를 확인하며 프롬프트에 4K를 적었다는 이유만으로 해상도를 충족했다고 하지 않는다. 특정 구성요소의 상세 흐름에는 별도로 지정된 비율을 선택할 수 있다.

전체 아키텍처의 제목은 좌측 상단에 정확히 **AWS 보안 관제**로 표시한다. 부제나 슬로건은 넣지 않는다. 현대오토에버 로고는 우측 상단에 배치하고, 제목·로고 영역 아래에서 시스템 그림을 시작한다.

**완전성과 밀도.** 1번 페이지(전체 아키텍처)는 노드 수 상한을 두지 않는다. README의 “구현한 기술” 표에 있는 모든 기술이 그림에 있어야 하며 누락은 결함이다. 화살표 수에도 상한은 없지만 선끼리 교차하거나 노드·글자를 통과하지 않도록 배치로 해결한다. 같은 역할의 서로 다른 서비스는 그룹 박스 하나에 나란히 둘 수 있다(예: 탐지 서비스 묶음). 노드 안에는 서비스명과 역할 한 줄만 쓴다. E1·F2 같은 ID 태그, 각주, 조건 설명 문장, 우측 보조 패널, 하단 설명 문장은 넣지 않는다. 영역 사이와 노드 주변에는 라벨과 연결선이 겹치지 않을 여백을 확보하며, 여백을 줄이려고 글자를 키우거나 요소를 겹치지 않는다.

**아이콘은 서비스당 하나, 선은 관계마다 하나.** 같은 AWS 서비스의 아이콘은 그림 전체에서 무조건 하나만 둔다. 그 서비스와 연결된 대상이 여럿이면(예: Lambda 하나에서 여러 서비스로) 아이콘을 복제하거나 선을 하나로 묶지 않고, 하나의 아이콘에서 대상마다 선을 각각 그린다. 한 아이콘에서 나가는 선은 접속 지점을 나누어 부채꼴로 펼치고, 같은 서비스에 속한 여러 리소스(예: Lambda 함수들)의 이름은 아이콘 옆 짧은 라벨 목록으로 적는다.

**전체 배치는 3행이다.** 위에서 아래로 읽으며 세 번째 행만 좌→우로 읽는다.

1. **행 1 — 01 IaC · 배포 제어.** 저장소, CI 계획, Terraform, 상태 관리를 가로 한 줄의 낮은 띠로 둔다.
2. **행 2 — 02 보호 대상 인프라.** 가장 큰 영역이다. 인터넷 사용자 경계, ALB, 서브넷, 서비스와 관제 대시보드의 배치를 표시한다.
3. **행 3 — 좌 03 탐지 · 수집, 우 04 SOAR · 상태 · 조치 · 관제.** 같은 높이로 나란히 두고 03에서 04로 좌→우로 흐른다. 두 영역 사이의 finding·알람 흐름은 03의 각 서비스 아이콘에서 04의 해당 대상으로 선을 각각 그린다.

각 영역의 좌측 상단에는 주색 번호 헤더(01~04)를 둔다. 영역 간 연결은 다음 네 가지만 세로 또는 가로 연결로 표시한다: 01→02 배포, 02→03 로그·finding, 03→04 finding·알람, 04→02 조치(SSM 실행)와 조회. 연결선이 다른 영역이나 노드를 통과하지 않도록, 가능한 범위에서 04가 조치·조회하는 대상(Private 자원과 관제 대시보드)은 02의 오른쪽에, 로그와 finding을 내보내는 대상은 02의 왼쪽에 둔다.

VPC 내부의 서브넷은 좌우 수평으로 나란히 배치한다. 현재 로컬 구성의 Public Web, Public Web B, Private App, Private DB는 서로 다른 서브넷으로 표시하며, 두 Public 서브넷을 하나로 합치거나 Private 자원을 인터넷 진입점처럼 그리지 않는다. 관제 대시보드는 실제 Private App 배치와 관제 역할(04 소속)을 함께 표시한다. 보안 그룹과 NACL은 전체 아키텍처 그림에서 프레임으로 그리지 않는다.

**VPC, 서브넷, EC2는 아이콘이 아니라 테두리로 표현한다.** VPC 테두리 안에 서브넷 테두리를, 서브넷 테두리 안에 EC2 인스턴스 테두리를 중첩하고, 각 테두리의 좌측 상단에 이름 라벨을 붙인다. EC2 안에서 동작하는 컨테이너·프로세스(예: Nginx, Flask, MySQL)는 해당 EC2 테두리 안의 라벨 상자로 둔다. VPC·서브넷·EC2에는 서비스 아이콘 노드를 따로 두지 않으며, 이 세 가지의 연결선은 해당 테두리의 접속 지점에 잇는다. 실제로 서로 다른 EC2 인스턴스는 각각 별도 테두리로 그린다.

**누락하지 않을 항목.** README 표의 모든 행 외에 특히 다음을 반드시 그린다: Amazon Bedrock, IAM 역할, GitHub OIDC, Secrets Manager, KMS, 그리고 관제 대시보드의 **AI 챗봇**과 **AI 보고서 작성** 기능. 관제 대시보드 EC2 테두리 안에는 대시보드 기능 라벨 상자(AI 챗봇, AI 보고서 작성, 원클릭 조치 등)를 두고, AI 챗봇과 AI 보고서 작성 상자에서 Bedrock 아이콘으로 선을 각각 그린다. 모델 표기는 코드의 모델 ID 변수에 있는 모델만 쓴다. 코드에 없는 모델은 채택이 결정 문서에 확정되기 전에는 그리지 않는다.

**Amazon Bedrock은 모든 아키텍처 페이지에 표기한다.** 연결선은 그 페이지의 범위에서 실제로 Bedrock을 호출하는 기능(대시보드 AI 챗봇, AI 보고서 작성, 허니팟)에만 그린다.

**추후 개선점 영역.** 1번 페이지 한쪽에 “추후 개선점” 영역을 점선 테두리로 두고, 아직 구현되지 않은 항목을 라벨 목록으로 적는다. 기본 항목은 전송·저장 암호화 범위 확대, HTTPS 및 접속 범위 제한, 조치 이력의 DynamoDB 통합이다. 이 영역의 항목에는 아이콘과 실선 연결을 쓰지 않는다. 이미 구현된 암호화(EC2 볼륨, CloudTrail KMS, Terraform state)는 본 구성에 정상 표기한다. 항목의 근거는 README의 “구현할 기술” 표와 decisions.md의 OPEN 항목이다.

03 안의 탐지 소스는 병렬 관계로 좌우에 나란히 두고 순차 처리 체인으로 연결하지 않는다. 04 안의 구성요소는 03에서 들어오는 방향(EventBridge·Lambda)에서 저장·알림·관제 방향으로 좌→우 순서를 따른다. 배치 순서만으로 새 처리 관계를 만들지 않는다.

각 노드 주변에 연결선과 라벨을 위한 여백 및 접속 지점을 확보한다. 직각 꺾임과 분기점을 활용하고, 선이 아이콘·텍스트·관계없는 노드를 통과하지 않게 한다. 연결선을 줄이기 위해 같은 노드를 다른 위치에 복제하지 않는다.

기능별 다이어그램은 상위 책임 경계와 대상 시스템을 보여 준 뒤 흐름을 진행 방향대로 배열한다. 조건부로 생성되는 구성요소에는 “선택”, “토글”, “조건부”를 표기한다. 개념상 연결과 실제 구현 연결을 혼합하지 말고, 미구현 목표는 구현 요소와 섞지 않고 “추후 개선점” 점선 영역에만 둔다.

### 2.3 로고, 아이콘, 도형

**AWS 공식 참조 아키텍처 스타일**을 따른다. 흰색 바탕에 평면 벡터로 그리고, 공식 서비스 아이콘은 모두 같은 크기로 두며 서비스명은 아이콘 아래 중앙에 한 줄로 쓴다. VPC, 서브넷, EC2 인스턴스는 아이콘이 아닌 얇은 테두리와 이름 라벨로 표현한다. 프레임과 아이콘 밖의 장식(그림자, 그라데이션, 큰 배경 도형)은 쓰지 않는다.

- 현대오토에버 로고는 승인된 원본 이미지를 우측 상단의 독립된 여백에 배치하고 원본 비율, 여백, 색을 유지한다. 원본이 없으면 로고 영역을 비워 두고 후편집으로 원본을 삽입하며, 로고 적용 전 결과는 초안으로 표시한다. AI에게 로고를 새로 그리거나 글자를 재구성하게 하지 않는다. 로고는 시스템 구성요소가 아니며 화살표로 연결하지 않는다.
- 최종 발표 이미지의 AWS 서비스는 공식 AWS 아키텍처 아이콘 에셋을 사용한다. 크기와 렌더링 규격을 통일하고 실제 서비스 이름을 함께 적는다. 공식 에셋을 사용할 수 없는 단계에서는 중립 도형과 정확한 라벨로 초안을 만들고 “공식 아이콘 적용 대기”로 표시한다. 유사 아이콘을 생성한 결과를 공식 아이콘으로 취급하지 않는다.
- 같은 AWS 서비스의 아이콘은 그림 전체에서 무조건 하나만 둔다. 그 서비스를 쓰는 대상이 여럿이면 하나의 아이콘에서 대상마다 선을 각각 그리며, 아이콘을 복제하거나 선을 하나로 묶지 않는다. 같은 서비스의 서로 다른 리소스(Lambda 함수, S3 버킷, DynamoDB 테이블 등)는 아이콘 옆 라벨 목록으로 구분하고 하나의 실제 리소스로 합치거나 다른 서비스 아이콘으로 바꾸지 않는다. EC2 인스턴스는 아이콘 없이 인스턴스마다 테두리 하나로 표현한다. Terraform state·잠금과 보안 데이터·조치 이력도 별도 리소스로 구분한다.
- Terraform, GitHub, Docker, Nginx, Flask, MySQL 등 제3자 소프트웨어 로고는 승인된 원본·공식 에셋을 사용한다. 로고가 없으면 제품명을 쓴 중립적인 라벨 상자를 사용한다.
- 행위자는 역할이 구별되는 단순한 회색 선화 또는 텍스트 라벨로 표현한다. 공격자 묘사는 위협 경로를 설명하는 데 필요한 수준으로 제한한다.
- 같은 종류의 리소스는 같은 도형 규칙을 사용한다. AWS 서비스, 데이터 저장소, 사용자, 네트워크 경계, 외부 연결을 모양으로 구분한다. 모양 의미를 문서 내에서 일관되게 유지한다.
- 아이콘 안에 글자를 생성하지 않는다. 서비스명은 아이콘 바깥의 라벨로 적는다.

### 2.4 타이포그래피와 라벨

한국어 고딕 계열의 가독성 높은 글꼴을 사용한다. 제목, 계층명, 구성요소명, 보조 설명 사이에 분명한 크기 차이를 둔다. 그림의 핵심을 이해하는 데 필요하지 않은 긴 문장을 노드 안에 넣지 않는다. 상세 설명은 발표 자료의 별도 텍스트나 설계 문서에 둔다.

설명과 범례는 한국어를 기본으로 한다. AWS 서비스명, 제품명, 코드 식별자, 정확한 리소스 이름은 원문 표기를 유지한다. 알 수 없는 이름을 비슷한 이름으로 바꾸거나 AI가 그럴듯한 라벨을 추가하지 않는다. 모든 텍스트는 출력 후 사람이 원본 요구와 대조한다. 이미지 생성 모델이 긴 한글이나 로고를 정확히 렌더링하지 못하면 배경·아이콘·레이아웃을 생성하고, 텍스트와 로고는 편집 도구에서 정식 자산으로 얹는다.

## 3. 흐름·상태 표현 규칙

각 화살표는 데이터 또는 제어의 출발점, 도착점, 방향, 의미를 나타낸다. 응답 흐름이 필요한 경우 요청과 응답을 구분한다. 화살표가 여러 개 교차하면 레이아웃을 다시 구성하거나 분기점을 명시한다.

| 표현 | 뜻 | 사용 조건 |
|---|---|---|
| 파란 실선 | 정상 트래픽 또는 정상 요청 경로 | 보호 대상 또는 서비스 간 요청 흐름 |
| 빨간 점선 | 공격·침투 시도 | 범위가 승인된 검증 경로에만 표시 |
| 회색 실선 | 로그·텔레메트리 수집 | 실제 또는 설계상 출처와 수집 대상이 문서에 있음 |
| 보라 점선 | 조회 요청 | 대시보드·상관분석기가 저장소나 AWS API에서 가져오는 데이터 |
| 하늘색 실선 | SOAR 자동 조치 | 이벤트가 실제 자동 조치 경로와 조건에 연결된 경우만 표시 |
| 별도 라벨이 있는 중립 연결 | 구성·소유·참조 관계 | 네트워크 트래픽이 아닌 관계를 나타낼 때 |

전체 아키텍처 그림에서도 흐름을 묶지 않고 관계마다 선 하나를 그린다. 한 서비스 아이콘에서 여러 대상으로 이어지면 아이콘 하나에서 대상마다 선을 따로 낸다. 라벨은 “요청”, “로그”, “조회”, “실행”처럼 한국어 2~6자로 쓴다. 번호 콜아웃은 README의 대표 흐름 순서에 해당하는 1~8번에 한정하고, 번호는 원형 배지로 그려 영역 번호(01~04) 헤더와 구별한다.

선의 색상만으로 데이터의 신뢰성이나 실행 성공을 의미하지 않는다. 조치 흐름은 입력 이벤트부터 조건 검사, 실행 서비스, 결과 기록, 대상 재검증까지 끊김 없이 구분한다. “이벤트 수신”, “SSM 요청”, “실행 성공”, “재검증 통과”를 하나의 성공 화살표로 축약하지 않는다.

자동 조치가 아닌 수동 절차는 자동 조치 색을 사용하지 않는다. 사람의 승인·검토가 계약에 포함되면 승인자와 승인 지점을 표시한다. 반대로 설계에 없는 승인 게이트를 이미 존재하는 자동 경로에 새로 그려 넣지 않는다. 향후 목표나 보류 중 정책은 구현 경로와 다른 점선 테두리·주석으로 나타내고 “제안” 또는 “미결정”이라고 표기한다.

데이터가 없거나 결과를 확인할 수 없는 상태는 “0건”, “해결”, “차단 완료”로 그리지 않는다. 필요할 때 “조회 실패”, “부분 수집”, “결과 확인 필요”, “재검증 대기”와 같은 라벨을 사용한다.

## 4. 기술 사실 검증과 미결정 사항

이미지 작성 전에 다음 근거를 확인한다.

1. 전체 경계와 목표는 README.md를 읽는다.
2. 구성요소의 책임·인터페이스·상태·실패 동작은 해당 기능의 설계 문서를 읽는다.
3. 사용자 확정 정책과 미결정 질문은 decisions.md를 읽는다.
4. 구현 상태를 그림에 담아야 할 때만 tracking.md의 코드 경로·검증 근거를 대조한다.
5. 시나리오 공격 경로와 증적 요구는 security-scenarios.md를 확인한다.

다이어그램의 모든 주요 화살표는 출발·도착 요소와 계약 근거를 추적할 수 있어야 한다. 그림 아래 설명 또는 함께 배포되는 검토 자료에는 핵심 인터페이스의 입력, 출력, 식별자, 이벤트 계약을 요약한다. 구현 확인 여부가 필요한 발표물은 정적 코드 확인과 실제 통합·실환경 검증을 분리해 표시한다.

레거시 README, 이전 이미지, 기존 AI 프롬프트는 사실 확인이 필요한 참고 자료다. 충돌이 있으면 승인된 최신 설계와 결정 기록을 따른다. 특히 AI 허니팟은 DEC-020·021·037로 구현 범위가 확정됐다(`enable_honeypot` 토글의 선택 구성, Bedrock Nova Lite, `HONEYPOT` 목록이 있을 때만 NACL 자동 차단, DynamoDB `ip_blocklist`). 그림에는 이 확정 구성만 그리고 "선택·토글"로 표기한다. 이전 프롬프트의 Beelzebub, OpenAI, `ai_suggestions_table`, 접속 즉시 무조건 차단은 채택하지 않았으므로 그리지 않는다. 세션 원문 보존·개인정보·비용 상한은 미결정(OPEN-011)이라 필요하면 미결정으로 분리해 표시한다.

## 5. 생성형 이미지 프롬프트 기본 양식

아래 양식을 새 이미지 작업의 출발점으로 사용한다. 대괄호 부분은 승인된 문서에서 확인한 값으로 채우며, 근거가 없으면 비워 두거나 “미결정”이라고 쓴다.

```
역할: 승인된 기술 설계를 정확하고 읽기 쉬운 AWS 공식 참조 아키텍처 스타일의 발표용 요약 다이어그램 한 장으로 표현하는 정보 시각화 디자이너.

목표:
- 제목: AWS 보안 관제. 좌측 상단에 정확히 표시. 부제·슬로건 없음.
- 범위: [그림이 설명할 범위와 기준점]
- 용도: [전체 아키텍처 요약 / 기능 흐름 / 보안 시나리오 / 발표용 요약]
- 기준 문서: [README.md의 “구현한 기술” 표와 해당 기능 설계·시나리오 문서]
- 독자: [관제 담당자 / 개발자 / 의사결정자]
- 형식: 16:9 가로형 PNG, 실제 출력 크기 3840×2160 픽셀(4K UHD).
- 완전성: 1번 페이지는 README의 “구현한 기술” 표의 모든 기술을 포함(누락 금지). 노드·화살표 수 상한 없음, 선 교차·겹침 금지. 리소스 식별자와 긴 조건 주석은 그리지 않음.
- 언어: 한국어. AWS·제품명 및 정확한 코드 식별자는 원문 표기.

기술 사실:
- 구성요소: [정본 문서에 있는 이름과 책임만 입력]
- 흐름: [출발점 → 도착점, 방향과 라벨을 명시]
- 경계: [계층·VPC·서브넷·보호 대상·관제 시스템 구분]
- 조건: [선택 리소스, 토글, 권한·정책 조건]
- 미결정: [미결정 항목을 목록화하고 현재 구성처럼 표현하지 않음]

시각 규칙:
- AWS 공식 테마: 흰색 바탕, 평면 벡터, 같은 크기의 공식 아이콘 아래 중앙에 서비스명, 얇은 그룹 프레임. 영역 헤더는 AWS 다크 네이비(#232F3E), 아이콘과 그룹 프레임의 색은 AWS 공식 아키텍처 아이콘 가이드를 따름. 현대오토에버 색은 로고에만 사용.
- 전체 시스템도는 3행 배치. 행 1은 01 IaC·배포 제어(낮은 가로 띠), 행 2는 02 보호 대상 인프라(가장 큰 영역), 행 3은 좌측 03 탐지·수집과 우측 04 SOAR·상태·조치·관제를 같은 높이로 나란히 두고 좌→우로 연결. 영역 헤더는 좌측 상단에 01~04 번호와 이름.
- VPC, 서브넷, EC2는 아이콘이 아닌 얇은 테두리와 좌측 상단 이름 라벨로 표현. VPC ⊃ 서브넷 ⊃ EC2 순서로 중첩하고, EC2 안의 컨테이너·프로세스는 라벨 상자. VPC 내부 서브넷은 좌우 수평 배치. 실제 서브넷 경계와 자원 위치를 유지. 보안 그룹·NACL 프레임은 그리지 않음.
- 반드시 포함: Amazon Bedrock, IAM 역할, GitHub OIDC, Secrets Manager, KMS, 관제 대시보드의 AI 챗봇과 AI 보고서 작성(EC2 테두리 안 라벨 상자, 각각 Bedrock 아이콘으로 선 연결). Bedrock은 모든 아키텍처 페이지에 표기. 모델 표기는 코드의 모델 ID와 일치하는 것만.
- “추후 개선점” 점선 영역: 전송·저장 암호화 범위 확대, HTTPS 및 접속 범위 제한, 조치 이력의 DynamoDB 통합. 이 영역에는 아이콘과 실선 연결을 쓰지 않음.
- 영역 간 연결은 01→02 배포, 02→03 로그·finding, 03→04 finding·알람, 04→02 조치·조회만 표시. 흐름은 묶지 않고, 한 서비스 아이콘에서 여러 대상으로 이어지면 아이콘 하나에서 대상마다 선을 각각 그림.
- 정상 흐름은 파란 실선, 공격은 빨간 점선, 로그 수집은 회색 실선, 조회는 보라 점선, 연결이 확인된 자동 조치는 하늘색 실선으로 표시하고 각 흐름에 2~6자 한국어 라벨을 둠. 번호 콜아웃은 원형 배지 1~8번까지만 사용.
- 노드 라벨은 서비스명과 역할 한 줄. ID 태그, 각주, 조건 설명 문장, 보조 패널, 하단 설명 문장을 넣지 않음.
- 노드 주변에 연결 여백과 접속 지점을 확보하고 직각 연결·분기점을 사용하여 선 교차와 아이콘·텍스트 통과를 없앰.
- AWS 공식 아키텍처 아이콘 에셋을 사용하며 서비스별 아이콘은 무조건 한 번만 배치(예: Lambda 아이콘 하나에서 여러 서비스로 선을 각각 연결). 같은 서비스의 여러 리소스 이름은 아이콘 옆 짧은 라벨 목록으로 표기. 아이콘 복제 금지.
- 우측 상단에 승인된 현대오토에버 원본 로고를 배치. 로고를 생성하거나 화살표로 연결하지 않음. 원본이 없으면 영역을 확보하고 후편집으로 삽입.
- 공식 아이콘이나 원본 로고가 누락된 결과는 초안으로 표시하며 최종 발표 이미지로 취급하지 않음.

금지:
- 근거 없는 서비스, 데이터 흐름, 네트워크 경로, 권한, 자동 조치, 승인 게이트, 임계값 또는 구현 상태 추가.
- 미결정 기능을 현재 구현처럼 표시.
- 실환경 조회 실패를 0건 또는 정상 상태로 표시.
- 실행 결과 미확인을 성공·실패·해결 완료로 단정.
- 외부 공격자가 근거 없는 네트워크 경로로 프라이빗 자원에 직접 연결되는 것으로 표현.
- 기술 설계의 의미를 시각적 대칭이나 공간 절약을 위해 변경.
- 노드·화살표 수 상한을 넘기기 위해 글자를 줄이거나 요소를 겹쳐 배치.

산출 후 자체 점검:
- 모든 주요 구성요소와 화살표가 기준 문서와 일치하는지 확인.
- 라벨, 방향, 계층, 경계, 범례와 조건부 요소를 확인.
- 실제 출력이 3840×2160 픽셀인지, 좌측 상단 제목과 우측 상단 원본 로고가 있는지 확인.
- 3행 배치, VPC·서브넷·EC2 테두리 표현, VPC 서브넷 수평 배치, README “구현한 기술” 표의 모든 행 포함, AWS 공식 에셋 사용, 서비스 아이콘 중복 없음, 연결선 접속 지점을 확인.
- 글자 겹침과 선 교차가 없는지 확인.
- 이미지 안의 한글과 제품명을 원문과 대조하고, 깨진 텍스트는 편집 가능한 방식으로 교체.
- 기술 검토를 통과하기 전까지 결과를 승인된 아키텍처 그림으로 표시하지 않음.
```

이 양식은 시각 작업 지침이다. AI에게 기준 설계 문서를 읽히지 않은 채 양식만 제공하거나, 프롬프트가 기술 검토를 대신한다고 보지 않는다.

## 6. 이미지 품질 검수 및 반영

발표 자료에 포함하기 전에 아래 항목을 모두 확인한다.

- [ ] 제목과 범위가 설명 대상과 일치한다.
- [ ] 전체 발표 이미지는 16:9, 실제 3840×2160 픽셀이며 좌측 상단 제목은 “AWS 보안 관제”다.
- [ ] 우측 상단에 승인된 현대오토에버 원본 로고가 있고 원본 비율·여백을 유지한다.
- [ ] 전체 그림은 3행 배치(01 IaC → 02 보호 대상 → 03 탐지·수집에서 04 SOAR·관제로 좌→우)를 유지하고, 세부 그림은 해당 기능의 경계만 표현한다.
- [ ] README “구현한 기술” 표의 모든 행이 그림에 있다(Bedrock, IAM, GitHub OIDC, Secrets Manager, KMS, AI 챗봇, AI 보고서 작성 포함). ID 태그·각주·긴 설명 문장은 없다.
- [ ] Amazon Bedrock이 모든 아키텍처 페이지에 표기되어 있고 모델 표기가 코드의 모델 ID와 일치한다.
- [ ] “추후 개선점” 점선 영역이 있으며 구현된 요소와 섞여 있지 않다.
- [ ] VPC의 서브넷이 좌우 수평으로 구분되어 있고, 03과 04가 같은 행에 좌→우로 놓여 있다.
- [ ] AWS 공식 아이콘 에셋을 사용하며 같은 서비스의 아이콘은 하나뿐이다. 그 서비스와 연결된 대상마다 하나의 아이콘에서 선이 각각 나온다.
- [ ] VPC, 서브넷, EC2는 아이콘이 아닌 테두리이며 VPC ⊃ 서브넷 ⊃ EC2 순으로 중첩되어 있다.
- [ ] 구성요소 이름·소유 계층·네트워크 위치가 기준 문서와 일치한다.
- [ ] 각 화살표의 출발점·도착점·방향·의미가 근거 문서에서 확인된다.
- [ ] 조건부 요소, 자동·수동 경로, 제안·미결정 상태가 눈에 띄게 구분된다.
- [ ] 관제 시스템, 보호 대상, 시험 대상, 데이터 저장소를 혼동하지 않는다.
- [ ] 글자가 읽히고 오탈자·가짜 텍스트·잘못된 로고가 없다.
- [ ] 공격·자동 조치·로그·조회 의미를 색상과 선 형태 및 라벨로 함께 전달한다.
- [ ] 텍스트와 아이콘이 겹치지 않고, 화살표 교차가 흐름을 바꾸어 읽히게 하지 않는다.
- [ ] 연결선이 지정된 노드·그룹 접속 지점에 이어지며 아이콘·텍스트·관계없는 노드를 통과하지 않는다.
- [ ] 설명 이미지가 기술 설계 문서와 모순되지 않는다.

검토 통과 후 이미지 파일명이나 발표 자료의 캡션에 범위와 기준 문서 버전을 연결한다. 그림 수정만으로 요구사항이나 구현 현황을 갱신했다고 간주하지 않는다. 반대로 기술 아키텍처가 바뀌면 영향받는 이미지를 찾아 갱신한다.
