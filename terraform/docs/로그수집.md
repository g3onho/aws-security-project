# 로그 수집 경로

이 인프라가 실제로 수집하는 로그를 Terraform 코드 기준으로 정리한다.
코드에 없는 것은 적지 않는다. 각 항목에 정의 위치(파일:라인)를 붙였다.

---

## 1. 한눈에 보기

| # | 로그 | 수집 대상 | 도착지 | 소비자 | 보존 |
|---|---|---|---|---|---|
| ① | VPC Flow Logs | VPC 전체 트래픽(ALL) | `/soar-sec/dev/vpc/flowlogs` | GuardDuty, 사람 | 14일 |
| ② | CloudTrail | 전 리전 API 호출 | S3 `soar-sec-dev-cloudtrail-<계정>` | GuardDuty, 포렌식 | 버킷 수명주기 |
| ③ | Nginx | `/var/log/nginx/access.log`·`error.log` | `/soar-sec/dev/web/nginx` | 사람 | 14일 |
| ④ | MySQL | `/var/log/mysql/error.log`·`general.log` | `/soar-sec/dev/db/mysql` | **메트릭 필터 → 알람** | 14일 |
| ⑤ | 수동 점검 결과 | nmap·Trivy 출력 | S3 `soar-sec-dev-scan-results-<계정>` | 대시보드, 사람 | 무기한 |
| ⑥ | Lambda 실행 로그 | `correlator`·`asr_trigger` stdout | `/aws/lambda/soar-sec-dev-*` | 디버깅 | 무기한 |

로그 그룹 이름은 `main.tf:16-18`에서 조립한다.

```hcl
log_group_nginx    = "/${var.project}/${var.env}/web/nginx"
log_group_mysql    = "/${var.project}/${var.env}/db/mysql"
log_group_flowlogs = "/${var.project}/${var.env}/vpc/flowlogs"
```

## 2. AWS가 직접 만드는 로그

에이전트 설치가 필요 없다. 리소스만 만들면 AWS가 알아서 쌓는다.

### ① VPC Flow Logs — `modules/network/flowlogs.tf:60`

```hcl
resource "aws_flow_log" "vpc" {
  traffic_type             = "ALL"          # 허용·거부 트래픽 모두
  log_destination_type     = "cloud-watch-logs"
  max_aggregation_interval = 60             # 1분 단위 집계
}
```

VPC 안에서 오간 트래픽의 **출발지·목적지·포트·허용여부**를 기록한다. 패킷 내용은 담기지 않는다.

**Flow Logs는 finding을 받는 쪽이 아니라 만드는 쪽이다.** GuardDuty가 이 로그를 읽어 이상 통신을 탐지한다. 코드 주석(`flowlogs.tf:3-4`)에도 같은 경고가 적혀 있다.

- 스위치: `enable_flow_logs` (기본 `true`)
- 전용 IAM 역할 `soar-sec-dev-flowlogs-role`이 로그 그룹에만 쓰기 권한을 가진다

### ② CloudTrail — `modules/security/cloudtrail.tf:129`

```hcl
resource "aws_cloudtrail" "this" {
  include_global_service_events = true
  is_multi_region_trail         = true
  enable_log_file_validation    = true      # 로그 위변조 검증
  kms_key_id                    = ...       # KMS 암호화
}
```

**누가 · 언제 · 어떤 API를 호출했는가**를 남긴다. "루트 계정으로 DescribeRegions 호출" 같은 GuardDuty 탐지가 여기서 나온다.

세 가지가 함께 켜져 있는 것이 핵심이다 — 전 리전 수집, 로그 파일 검증, KMS 암호화. 감사 증적으로 쓰려면 셋 다 필요하다.

- 스위치: `enable_cloudtrail` (기본 `true`)
- 버킷은 `force_destroy = false` (`cloudtrail.tf:52`) — 실수 삭제 방지. **`terraform destroy` 시 객체를 수동으로 비워야 한다.**

## 3. CloudWatch Agent가 보내는 로그

EC2 안의 **파일**을 읽어 올린다. 에이전트가 설치·기동돼 있어야 한다.

### ③ Nginx — `modules/compute/templates/docker-host.sh.tftpl:45-46`

```json
{ "file_path": "/var/log/nginx/access.log", "log_group_name": "...", "log_stream_name": "{instance_id}/access" },
{ "file_path": "/var/log/nginx/error.log",  "log_group_name": "...", "log_stream_name": "{instance_id}/error" }
```

access와 error를 **스트림으로 분리**한다. 인스턴스 ID가 스트림 이름에 들어가 여러 대를 같은 그룹에서 구분한다.

### ④ MySQL — `modules/compute/templates/mysql-db.sh.tftpl:58-59`

```json
{ "file_path": "/var/log/mysql/error.log",   "log_stream_name": "{instance_id}/error" },
{ "file_path": "/var/log/mysql/general.log", "log_stream_name": "{instance_id}/general" }
```

**이 로그만 자동 탐지에 직접 쓰인다.** 나머지는 사람이 보는 용도다.

```
MySQL error.log
  → 메트릭 필터  "Access denied for user"     (soar/cloudwatch.tf:78)
  → 지표         soar-sec-dev/security · MySQLAuthFailure
  → 알람         5분간 10회 이상               (soar/cloudwatch.tf:91)
  → SNS          담당자 알림
```

무차별 대입 탐지(SEC-06)가 이 경로다. 로그 문자열 하나가 지표가 되고, 지표가 알람이 된다.

## 4. 로그가 아닌 수집물

### ⑤ 수동 점검 결과 — `modules/soar/storage.tf:44`

SSM 문서가 EC2에서 도구를 실행하고 결과 파일을 S3에 올린다.

| 문서 | 도구 | S3 경로 |
|---|---|---|
| `SCAN-PortAndWeb` | nmap, curl | `s3://<버킷>/portweb/<타임스탬프>.txt` |
| `SCAN-ContainerImage` | Trivy | `s3://<버킷>/trivy/<타임스탬프>.txt` |

스트리밍이 아니라 **실행할 때마다 파일 하나**가 생긴다. 사람이 SSM으로 돌려야 한다.

## 4-1. 로그가 아닌 것 — finding 은 어디로 가나

**보안 그룹 변경이나 GuardDuty 탐지는 CloudWatch Logs 로 가지 않는다.**
각 서비스가 자체 저장소를 쓰고, 판정 결과만 Security Hub 로 모인다.
"GuardDuty 로그를 어디서 보냐"는 질문에 답이 없는 이유다 — GuardDuty 는
로그를 **만드는** 쪽이 아니라 **읽는** 쪽이다(입력: Flow Logs · CloudTrail · DNS).

### 보안 그룹 — AWS Config 경로

```
SG 변경
  → Config 가 구성 항목(Configuration Item) 기록
  → S3  soar-sec-dev-config-<계정>          ← 구성 이력 원본
  → Config 규칙 평가 (restricted-ssh 등 4개)
  → Security Hub finding
  → EventBridge(sh-asr) → Lambda asr_trigger
  → DynamoDB soar-sec-dev-remediation-actions
```

**Config 가 감시하는 리소스는 7종뿐이다** (`modules/security/config.tf:118-130`).
비용 때문에 전체 기록을 껐다. 목록에 없는 리소스는 바뀌어도 기록되지 않는다.

```hcl
recording_group {
  all_supported = false
  resource_types = [
    "AWS::EC2::SecurityGroup",   # 보안 그룹
    "AWS::EC2::Instance",
    "AWS::EC2::NetworkAcl",
    "AWS::IAM::Role",
    "AWS::IAM::User",
    "AWS::S3::Bucket",
    "AWS::CloudTrail::Trail",
  ]
}
```

### GuardDuty — EventBridge 2갈래

```
GuardDuty 탐지
  → GuardDuty 자체 저장소 (90일, AWS 관리)
  → Security Hub 자동 전달
  → EventBridge 규칙 2개 (modules/soar/eventbridge.tf)
       gd-correlator → Lambda correlator  → DynamoDB correlated-findings
       gd-asr        → Lambda asr_trigger → DynamoDB remediation-actions
```

규칙이 나뉜 이유는 소비자가 다르기 때문이다. `correlator` 는 Inspector CVE 와 합쳐
대시보드에 보여줄 상관분석 레코드를 만들고, `asr_trigger` 는 자동 조치를 판정한다.
Config·Inspector·Access Analyzer 결과는 Security Hub 를 거쳐 `sh-asr` 한 갈래로만 간다.

### 종류별 저장 위치

| 종류 | 예 | 저장 위치 | 성격 |
|---|---|---|---|
| 로그 | Flow Logs, Nginx, MySQL | CloudWatch Logs | 원본 기록, 시간순 |
| 로그 | CloudTrail | S3 (+KMS) | 원본 기록, 감사용 |
| 구성 이력 | 보안 그룹 변경 | S3 (Config 버킷) | 스냅샷 |
| **finding** | GuardDuty · Inspector · Config 규칙 · Access Analyzer | 각 서비스 → **Security Hub** | 판정 결과 |
| 조치 이력 | 자동·수동 대응 기록 | DynamoDB | 이 프로젝트가 직접 기록 |

**대시보드가 읽는 것은 finding 과 조치 이력이다.** CloudWatch Logs 는 직접 조회하지 않는다.
MySQL 로그만 메트릭 필터를 거쳐 간접적으로 알람이 된다(4절 ④).

## 5. 수집이 실패하는 조건

에이전트 로그(③④)는 **네트워크 경로 두 개**에 의존한다. 하나라도 없으면 조용히 실패한다.

| 필요한 것 | 없으면 | 해결 |
|---|---|---|
| 에이전트 설치 경로 | 설치 자체가 안 됨 | 리전 S3 버킷 URL 사용 (`docker-host.sh.tftpl:27`) |
| `logs` VPC 엔드포인트 또는 NAT | 에이전트는 돌지만 **전송 실패** | `logs` 엔드포인트 추가 |

### 실제로 겪은 사례

**에이전트가 설치되지 않았다.** user_data가 글로벌 S3 엔드포인트(`amazoncloudwatch-agent.s3.amazonaws.com`)에서 받으려 했는데, S3 게이트웨이 엔드포인트는 **같은 리전 S3만** 라우팅한다. NAT가 없어 다운로드가 실패했고, `|| true`가 그 실패를 삼켜 아무 흔적 없이 넘어갔다.

→ 리전 버킷(`amazoncloudwatch-agent-${region}.s3.${region}.amazonaws.com`)으로 교체해 해결.

**설치해도 지표가 안 갔다.** `monitoring` VPC 엔드포인트가 없어 `PutMetricData`가 나갈 곳이 없었다. 에이전트 상태는 `running`이라 정상으로 보였다.

→ `modules/network/main.tf:161`의 인터페이스 엔드포인트 목록에 `monitoring` 추가.

**로그는 아직 같은 문제가 남아 있다.** `logs` 엔드포인트가 없어 ③④가 전송되지 않는다. 메모리 지표와 똑같은 원인이다.

```hcl
# modules/network/main.tf:161
interface_endpoints = ... toset(["ssm", "ssmmessages", "ec2messages", "monitoring"])
#                                                                     ↑ "logs" 추가 필요
```

엔드포인트당 월 $9 수준이고, NAT 게이트웨이(월 $40+)보다 싸다.

## 6. 켜고 끄는 변수

| 변수 | 기본값 | 영향 |
|---|---|---|
| `enable_flow_logs` | `true` | ① |
| `enable_cloudtrail` | `true` | ② |
| `enable_vpc_endpoints` | `true` | ③④ 전송 경로 |
| `enable_nat_gateway` | `false` | ③④ 전송 경로(대안) |
| `log_retention_days` | `14` | ①③④ 보존 기간 |
| `mysql_auth_fail_threshold` | — | ④ 알람 임계치 |

보존 기간은 CloudWatch Logs에만 적용된다. CloudTrail S3와 스캔 결과 S3는 별도 수명주기 정책을 따른다.

## 7. 확인 명령

```bash
# 로그 그룹 목록과 보존 기간
aws logs describe-log-groups \
  --query 'logGroups[].{Name:logGroupName,Retention:retentionInDays,Bytes:storedBytes}' \
  --output table

# 특정 그룹에 실제로 쌓이고 있는지
aws logs describe-log-streams \
  --log-group-name /soar-sec/dev/db/mysql \
  --order-by LastEventTime --descending --max-items 5

# CloudTrail 수집 상태
aws cloudtrail get-trail-status --name soar-sec-dev-trail

# 에이전트 상태 (EC2 안에서)
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a status
```

`storedBytes`가 0이면 그룹만 있고 로그가 안 들어온 것이다. 5절의 의존성부터 확인한다.
