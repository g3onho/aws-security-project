# Terraform 구성 설명

`aws-soar-terraform` (v10 + A 병합본) · 2026-09-18
이 문서는 **무엇이 어디에 있고, 왜 그렇게 나뉘어 있는지**를 설명합니다.
런타임 흐름(탐지 → 판단 → 조치)은 `docs/아키텍처.md`,
실행 절차는 `README.md`, 비용은 `docs/비용예측.md` 를 봐 주세요.

## 1. 전체 그림

```
루트 모듈 (main.tf)
│
├─ module.network   VPC · 서브넷 4개 · SG 8개 · NACL · Flow Logs · VPC 엔드포인트
├─ module.compute   EC2 5대 · ALB · ECR · IAM 역할 · Secrets Manager · AMI 조회
├─ module.security  GuardDuty · Inspector · Config · Access Analyzer · Security Hub · CloudTrail
└─ module.soar      EventBridge · Lambda 2개 · SSM 문서 7개 · SNS · DynamoDB · CloudWatch
```

선언 기준 리소스 173개, 변수 121개, 출력 49개입니다.
(`count` / `for_each` 때문에 실제 생성 개수는 토글에 따라 달라집니다.)
network → compute → security → soar 순으로 의존합니다. soar는 security가 만든
Security Hub finding을 입력으로 받기 때문에 가장 마지막입니다.

## 2. 루트 파일

| 파일 | 역할 |
|---|---|
| `versions.tf` | Terraform 1.6+ / AWS provider 6.x 버전 고정 |
| `providers.tf` | 리전·공통 태그(`default_tags`) 5종 · 공인 IP 자동 감지 |
| `variables.tf` | 입력 변수 전부. 토글은 여기서 확인합니다 |
| `main.tf` | 모듈 4개 호출과 변수 전달 |
| `outputs.tf` | 접속 주소·인스턴스 ID·SG ID 등 |
| `backend.tf` | **원격 state (S3 + DynamoDB 잠금). 값이 직접 들어 있습니다** |
| `backend.hcl.example` | 부분 구성 방식 예시. 계정 ID를 코드 밖에 둘 때 쓰는 대안 |
| `terraform.tfvars.example` | 값 채우기용 템플릿. 복사해서 `terraform.tfvars` 로 |
| `.gitignore` | state·tfvars·pem·tfplan 차단 (저장소 루트에도 따로 있습니다) |

### 원격 state

`backend.tf` 가 bootstrap 이 만든 버킷과 잠금 테이블을 직접 가리킵니다.

```hcl
bucket         = "soar-sec-tfstate-<ACCOUNT_ID>"
key            = "soar-sec/terraform.tfstate"
dynamodb_table = "soar-sec-tflock"
encrypt        = true
```

버킷 이름에 계정 ID가 들어가므로 **계정을 옮기면 이 파일을 함께 고쳐야 합니다.**
고친 뒤에는 `terraform init -reconfigure` 가 필요합니다. 그냥 `init` 만 하면
`Backend configuration changed` 로 막힙니다.

`backend.hcl` 방식(계정 ID를 저장소 밖에 두기)도 가능하지만, 그러면 CI 가
그 파일을 읽지 못해 워크플로를 함께 고쳐야 합니다. 지금은 코드에 직접 두는 쪽을 택했습니다.

### 공통 태그

`providers.tf` 의 `default_tags` 로 모든 리소스에 자동 부착됩니다.
리소스마다 태그를 쓰지 않는 이유는, 빠뜨릴 여지를 없애기 위해서입니다.

```hcl
Project = var.project   Environment = var.env   Team = var.team_name
Owner   = var.owner     ManagedBy   = "terraform"
```

학생가이드 7.3이 요구하는 5종입니다. `team_name` 과 `owner` 는 제출 전에 본인 값으로 바꿔 주세요.

### 공인 IP 자동 감지

```hcl
data "http" "my_ip" { url = "https://checkip.amazonaws.com/" }
```

`admin_cidr` 을 손으로 넣지 않아도 되지만, **plan 을 돌릴 때마다 외부 HTTP 호출이 발생**하고
집 IP가 바뀌면 손대지 않은 SG에도 매번 diff가 생깁니다. 오프라인 환경에서는 plan 자체가 실패합니다.
고정하고 싶으면 `admin_cidr` 을 직접 지정하면 됩니다.

## 3. module.network

| 파일 | 내용 |
|---|---|
| `main.tf` | VPC · 서브넷 4개 · IGW · 라우팅 · NAT(옵션) · VPC 엔드포인트 |
| `sg.tf` | Security Group 8개와 인그레스/이그레스 규칙 |
| `nacl.tf` | 서브넷 단위 NACL 규칙 7개 |
| `flowlogs.tf` | VPC Flow Logs → CloudWatch |

### 서브넷 4개

| 이름 | 성격 | 들어가는 것 |
|---|---|---|
| `public_web` | 퍼블릭 | DVWA · ALB · NAT |
| `public_web_b` | 퍼블릭 (2번째 AZ) | ALB 요구사항(최소 2 AZ) **전용** |
| `private_db` | 프라이빗 | MySQL EC2 |
| `private_app` | 프라이빗 | **Docker 호스트** · 대시보드 · 공격자 |

> Docker 호스트는 퍼블릭이 아니라 `private_app` 에 있습니다.
> 인터넷에 직접 노출되지 않고 ALB 또는 관리자 IP 를 통해서만 닿습니다.

### Security Group 연결 관계

고정 IP를 나열하는 대신 **앞 계층의 SG를 소스로 참조**합니다(학생가이드 6.1).
계층이 바뀌어도 허용 관계가 그대로 유지됩니다.

```
인터넷 ──80/443──▶ alb
                    │
                    └──▶ web_dvwa · docker_host
                                      │
                              3306 ───┴──▶ db_auto / db_manual
VPC 내부 ──5000──▶ dashboard   (SSM 포트 포워딩 경유)
```

**SSH 22번 규칙이 없습니다.** 접속은 Session Manager 전용입니다.
대시보드 5000도 `var.vpc_cidr` 로만 열려 있어 인터넷에서는 닿지 않습니다.

> ⚠️ `alb_http` / `alb_https` 는 `0.0.0.0/0` 입니다. 뒷단이 **DVWA(의도적으로 취약한 앱)** 이므로,
> 실습 중에는 `cidr_ipv4` 를 `var.admin_cidr` 로 좁히는 편이 안전합니다. `sg.tf` 두 줄입니다.

### db_auto / db_manual — SOAR 시연의 핵심

MySQL SG가 두 개인 이유는 **같은 위반에 다른 결과**를 보여주기 위해서입니다.
태그로 자동조치 대상 여부가 갈리고, 한쪽만 Lambda가 되돌립니다.
발표에서 "자동조치가 실제로 동작했다"를 보여주는 장치입니다.

### VPC 엔드포인트 (기본 on)

```
인터페이스 : ssm · ssmmessages · ec2messages   (Session Manager용)
게이트웨이 : s3                                  (무료)
```

**NAT Gateway 없이 프라이빗 서브넷에서 Session Manager를 쓰기 위한 구성입니다.**
NAT(시간당 $0.059)보다 인터페이스 엔드포인트 3개(시간당 약 $0.033)가 쌉니다.
다만 패키지 설치처럼 일반 인터넷 접근이 필요하면 `enable_nat_gateway = true` 가 따로 필요합니다.

## 4. module.compute

| 파일 | 내용 |
|---|---|
| `main.tf` | EC2 5대 + `local.common_metadata` |
| `ami.tf` | Ubuntu AMI 조회 (Canonical 소유자 ID 고정) |
| `alb.tf` | ALB · 타깃 그룹 · 리스너 · HTTPS 리다이렉트 |
| `ecr.tf` | 컨테이너 리포지토리 + 수명주기 정책 |
| `iam.tf` | EC2 역할과 인스턴스 프로파일 |
| `secrets.tf` | DB 비밀번호 Secrets Manager |
| `templates/*.sh.tftpl` | user-data 템플릿 5개 |

### EC2 5대

| 인스턴스 | 타입 · 위치 | 역할 | 토글 |
|---|---|---|---|
| `docker_host` | `t3.small` · private_app | 컨테이너 호스트 (보호 대상 서비스) | 상시 |
| `db` | `t3.small` · private_db | MySQL — 탐지·조치 대상 | 상시 |
| `dashboard` | `t3.micro` · private_app | Flask 관제 화면 | 상시 |
| `web_dvwa` | `t3.micro` · public_web | 취약한 웹앱 (공격 대상) | `enable_dvwa_instance` (기본 on) |
| `attacker` | `t3.micro` · private_app | 공격 트래픽 발생원 | `enable_attacker_instance` (기본 **off**) |

`attacker` 가 있는 이유: 공격 트래픽을 VPC 안에서 만들면 GuardDuty와 Flow Logs에 확실히 잡히고,
외부에서 스캔할 때 생기는 "허가 없는 대상 스캔" 문제(가이드 11장)를 피할 수 있습니다.

### 공통 메타데이터

```hcl
locals {
  common_metadata = { http_tokens = "required" }   # IMDSv2 강제
}
```

5대가 모두 이 값을 참조합니다. 인스턴스를 추가할 때 빠뜨릴 여지가 없습니다.
EBS는 전부 `gp3` + `encrypted = true` 입니다.

### user-data 를 `.tftpl` 로 두는 이유

학생가이드 5.4가 `templates/` 와 `.tftpl` 을 권장합니다.
`templatefile()` 로 Terraform 변수를 주입할 수 있어서, 셸 스크립트 안에서
문자열 치환을 하지 않아도 됩니다. DB 엔드포인트나 시크릿 이름처럼
apply 시점에야 정해지는 값을 넘길 때 차이가 납니다.

### HTTPS

```hcl
has_certificate = var.acm_certificate_arn != ""
ssl_policy      = "ELBSecurityPolicy-TLS13-1-2-2021-06"
```

인증서 ARN을 넣으면 80 → 443 리다이렉트와 TLS 리스너가 켜집니다.
비워두면 HTTP만 동작합니다. **도메인과 ACM 인증서가 없으면 이 경로는 비활성입니다** —
제출 시 잔여 위험으로 밝히면 됩니다.

## 5. module.security

탐지·수집 계층입니다. 파일이 서비스별로 나뉘어 있어 필요한 것만 열어 보면 됩니다.

| 파일 | 서비스 | 하는 일 |
|---|---|---|
| `guardduty.tf` | GuardDuty | 위협 인텔리전스 기반 이상 탐지 |
| `inspector.tf` | Inspector v2 | EC2·컨테이너 취약점 스캔 |
| `config.tf` | AWS Config | 규칙 4개로 설정 위반 감시 |
| `access_analyzer.tf` | IAM Access Analyzer | 외부 접근 가능 리소스 분석 (무료) |
| `securityhub.tf` | Security Hub | 위 결과를 한곳에 모으는 허브 |
| `cloudtrail.tf` | CloudTrail | API 감사 로그 + S3 + KMS |

이 모듈에는 `outputs.tf` 가 없습니다. 루트에서 참조하지 않는 출력만 있어서 지웠습니다.
탐지 서비스 활성 상태를 `terraform output` 으로 뽑아야 하면 루트 `outputs.tf` 에
블록을 하나 추가하면 됩니다.

### Config 규칙 4개

`restricted_ssh` 를 포함해 4개가 들어 있습니다.
이 규칙들이 SOAR 자동조치의 **트리거 근거**가 됩니다. 규칙이 위반을 감지하면
Security Hub로 finding이 올라가고, 그것을 EventBridge가 받습니다.

### CloudTrail

다중 리전 + 로그 파일 검증 + KMS 암호화 + S3 퍼블릭 차단까지 켜져 있습니다.
학생가이드 8장이 요구하는 "Log File Validation, 암호화, 접근 제한"을 모두 충족합니다.

## 6. module.soar

자동조치 계층입니다. **이 프로젝트의 차별점이 여기 있습니다.**

| 파일 | 내용 |
|---|---|
| `eventbridge.tf` | Security Hub finding → Lambda 라우팅 규칙 |
| `lambda.tf` | Lambda 2개 정의와 패키징 |
| `lambda_src/correlator/handler.py` | finding 상관관계 분석 |
| `lambda_src/asr_trigger/handler.py` | 자동조치 실행 판단 |
| `ssm.tf` | SSM 문서 등록 |
| `documents/*.yaml` | 실제 조치 플레이북 7개 |
| `storage.tf` | DynamoDB 2개 + S3 (스캔 결과) |
| `sns.tf` | 알림 |
| `cloudwatch.tf` | 알람과 대시보드 |

### 플레이북 7개

| 문서 | 조치 |
|---|---|
| `ASR-RevokeSecurityGroupIngress` | 열린 SG 규칙 회수 |
| `ASR-BlockIpWithNacl` | 공격 IP를 NACL로 차단 |
| `ASR-DisableExposedAccessKey` | 노출된 액세스 키 비활성화 |
| `ASR-RotateDbSecret` | DB 비밀번호 교체 |
| `ASR-HardenNginx` | Nginx 설정 강화 |
| `SCAN-PortAndWeb` | 포트·웹 점검 실행 |
| `SCAN-ContainerImage` | 컨테이너 이미지 스캔 |

YAML로 분리돼 있어 발표 때 문서 하나만 열어 보여주기 좋습니다.
`ASR-` 는 조치, `SCAN-` 은 점검입니다.

### 흐름

```
GuardDuty/Config/Inspector
   └─▶ Security Hub (finding)
        └─▶ EventBridge 규칙
             ├─▶ correlator Lambda   (여러 finding을 하나의 사건으로 묶음 → DynamoDB)
             └─▶ asr_trigger Lambda  (조치할지 판단 → SSM Automation 실행)
                  └─▶ documents/ASR-*.yaml
                       └─▶ SNS 알림 + DynamoDB 기록
```

게이트별 분기와 자동/수동 대조군 흐름은 `docs/아키텍처.md` 3~4장에 그림으로 있습니다.

## 7. 토글 (비용 통제)

`variables.tf` 의 `enable_*` 입니다. **기본값이 꺼져 있는 것이 비싼 것들입니다.**

| 변수 | 기본 | 켜면 드는 비용 |
|---|:---:|---|
| `enable_nat_gateway` | off | 시간당 $0.059 + 데이터 $0.062/GB |
| `enable_alb` | off | 시간당 $0.0225 + LCU |
| `enable_waf` | off | 월 $5 + 룰당 $1 |
| `enable_attacker_instance` | off | EC2 1대분 |
| `enable_vpc_endpoints` | **on** | 인터페이스 3개 × 시간당 약 $0.011 |
| `enable_dvwa_instance` | **on** | EC2 1대분 |
| 탐지 서비스 6종 | **on** | 사용량 기반. 체험 기간 확인 |

자세한 금액은 `docs/비용예측.md` 에 있습니다.

## 9. 주의할 것

1. **`terraform.tfvars` 는 커밋되지 않습니다.** 팀원과 값을 맞출 때는
   `terraform.tfvars.example` 을 고쳐서 공유해 주세요.
2. **`apply -auto-approve` 는 쓰지 않습니다.** plan에 `-/+ replace` 가 보이면
   무엇이 지워지는지 먼저 확인이 필요합니다. 특히 `aws_instance.db` 는 데이터가 사라집니다.
3. **콘솔에서 직접 고치면 드리프트가 생깁니다.** 긴급 조치가 아니면 코드를 고쳐서
   apply 하고, 콘솔에서 바꿨다면 즉시 코드에 반영한 뒤 `terraform plan` 으로 차이를 확인해 주세요.
4. **ALB가 인터넷에 열려 있습니다.** 뒷단이 DVWA이므로 실습 중에는 `admin_cidr` 로
   좁히는 것을 권합니다.
5. **종료 시** `terraform plan -destroy` 로 먼저 확인하고, destroy 후에도
   S3 버킷·KMS 키·CloudWatch 로그 그룹이 남아 있는지 콘솔에서 봐 주세요.
   CloudTrail 버킷은 `force_destroy = false` 라 객체가 남아 있으면 삭제가 실패합니다.
   state 버킷도 버저닝이 켜져 있어 **버전까지 지워야** 비워집니다.
6. **계정을 옮길 때는 자격증명부터 확인해 주세요.** bootstrap 의 버킷 이름은
   `data.aws_caller_identity` 로 만들어지므로, 프로파일이 잘못 잡혀 있으면
   엉뚱한 계정에 그대로 생성됩니다. `terraform apply` 전에 한 번:

   ```bash
   aws sts get-caller-identity
   ```

   Terraform 은 `--profile` 옵션이 없고 환경변수 `AWS_PROFILE` 만 봅니다.
   비어 있으면 `default` 프로파일을 씁니다.
7. **GitHub OIDC 는 레포 경로를 문자 그대로 비교합니다.** `bootstrap` 의
   `github_repo` 기본값이 실제 `owner/repo` 와 다르면 CI 가
   `Not authorized to perform sts:AssumeRoleWithWebIdentity` 로 막힙니다.
   레포 이름을 바꿨다면 `bootstrap` 을 다시 apply 해야 합니다.
